# Sessions и reporting

## Session ID

Каждый `backup` и `restore` получает стабильный session ID. Ручные границы не
создают новый запуск:

```bash
workspace-recover next <session>
workspace-recover continue <session> --set target=/work/project
```

После freeze plan `continue` использует plan из session и не перечитывает
изменившийся template.

## Information types

`info SESSION` показывает доступные типы данных, например `backup`, `restore`,
`verification`, `workflow`, `handoff`.

Каждый type имеет:

- `short` — минимальную сводку;
- `medium` — полезную расширенную информацию, определённую reporter profile;
- `full` — **только путь** к файлу первичной записи. Содержимое не печатается.

CLI не печатает после каждой операции полный список команд. Terminal output
содержит одну подсказку:

```text
More: workspace-recover info <session>
```

## Reporter profiles

Built-in profiles: `command-output`, `json`, `json-lines`, `junit`, `tap`,
`artifact-list`, `custom-command`.
`medium` не имеет универсального алгоритма: JUnit показывает тестовые counters,
provider-report — transport details, custom reporter — доменно полезную сводку.

Custom reporter запускается во время session и должен вернуть JSON с полями
`short` и `medium`. `info` позже только читает сохранённые artifacts и не
запускает
parser повторно.


## Сохранность первичных данных

Для каждого выполненного шага доступен тип `step:<id>`. Полный результат JSON,
JUnit или пользовательского parser сохраняется побайтно в каталоге сессии до
перехода к следующему шагу. Это сохраняет данные после явно объявленного cleanup
и удаления успешно проверенной clean room. Инструмент не ищет побочные изменения
рабочей области: копируется только объявленный источник отчёта.

Рядом сохраняются размер и SHA256 файла. `info` не выполняет parser повторно.
Полный отчёт handoff — отдельный JSON-файл с прочитанными обратно вложениями и
контрольными суммами, а не каталог или тело письма в терминале.


## Сбой операции и продолжение

Ошибка backup/restore сохраняет `error.json`, тип `error`, идентификатор сессии
и конкретную команду просмотра причины. При нестандартном `--state-dir` подсказка
включает этот каталог, чтобы повторная команда нашла ту же сессию.

`continue` с готовым plan не читает исходный template/manifest. Это распространяется
и на запуск непосредственно по manifest без генератора. Завершённая сессия не
выполняется повторно. Изменение исходного файла само по себе ничего не инвалидирует.

Ошибка parser не подменяется успешной сводкой: сохраняется `report-error.json` и
предупреждение. Исходный exit code команды остаётся неизменным; следующая объявленная
команда, включая cleanup, выполняется по прежним правилам manifest. Для verification
такое предупреждение не превращает восстановление в неуспешное.

Пока поддерживается продолжение на границах входных данных и аутентификации.
Произвольное аварийное завершение ОС посреди команды не имеет гарантии exactly-once:
нельзя считать его успешным или самовольно повторять изменяющую данные команду.


Полный запрос без information type:

```bash
workspace-recover info SESSION --view full
```

выдаёт только путь к `session.json`. С `--type` выдаётся только путь к первичному
файлу выбранного результата. Metadata/hash можно получить через сохранённые
receipt/report записи, но команда `full` не добавляет их в stdout.

## Доменные представления

| Профиль | Полезное medium | Объявленный источник |
|---|---|---|
| `command-output` | Код процесса, длительность и диагностический текст | stdout/stderr процесса |
| `junit` | Суммарные тесты, ошибки, пропуски и сообщения failures | `source` — JUnit XML |
| `tap` | Тесты, failures, skips и имена неуспешных случаев | stdout процесса |
| `json` | Содержимое JSON с ограничением объёма | `source` |
| `json-lines` | Число записей/байтов, счётчики level/status и ошибки | `source` |
| `artifact-list` | Список файлов, размеры и контрольные суммы | `sources` |
| `custom-command` | Значение `medium`, сформированное авторским parser | `argv` |

Универсального правила «первые два/последние два» нет. Реестр не выбирает тесты:
профиль относится к отчёту уже объявленной команды. Custom parser получает
`WR_PRIMARYPATH`, `WR_STDOUTPATH`, `WR_STDERRPATH`, `WR_WORKSPACE`; возвращает JSON
с `short`, `medium` и необязательным `fullPath`. Исходный файл сохраняется до
следующей команды. Зависимость parser от приложения задаёт автор manifest, а
не runtime-import инструмента.
