# Версия формата и выпуск приложения

Все собственные самостоятельные JSON-документы имеют поле `schema` текущего
семейства `workspace-recover/<kind>/v3`. Вложенные workflow/actions/reporters
версионируются содержащим их документом; JSON Schema описания имеют `$id` с той
же версией. Данные Google OAuth/API и пользовательские raw JSON/JUnit отчёты
имеют внешние форматы: их нельзя переименовывать заменой `/v1/` на `/v2/`.
Например, Gmail API остаётся `/gmail/v1/`, независимо от формата продукта.

Текущий исполняемый файл не читает `/v1`, неизвестные версии и документы без
обязательной версии. Автоматической миграции и fallback нет. Для старой копии
используется архив соответствующего старого выпуска. Сохранённый plan остаётся
действительным для создавшего его исполнителя; редактирование исходного manifest
не влияет на этот plan.

`requires.formatVersion` должен совпасть с текущим; неизвестные capability names
отклоняются. Версия npm/Python-программы согласуется в `package.json`, `pyproject.toml` и
Python package metadata, выводится через `--version`
и присутствует в `CHANGELOG.md`. Документы и skill входят в поставку.

## Кандидат и проверка выпуска

Разработка может содержать несколько проверенных commits одной готовящейся версии.
Публикация относится к одному принятому кандидату и его выбранному тегу, а не к
автоматической публикации каждого рабочего commit. Версию и данные v3 не смешивают.
Для запуска нужны Python/venv/pip и подготовленное окружение выбранной версии.

В подготовленном исходном checkout:

```bash
WORKSPACE_RECOVER_PYTHON=/usr/bin/python3.12 npm install
npm test
node scripts/release-check.mjs
```

Нужна доступная точная CE-зависимость. При локальной проверке допустим явно
выбранный полный offline wheelhouse; такой результат не подтверждает публичный
PyPI/npm. Обычный release-check проверяет материалы поставки и сообщает
`gitVerified=false`; он не создаёт tag, commit или registry publication.

Существующий `node scripts/release-check.mjs --git` дополнительно требует
самостоятельный корень Git, чистое дерево, текущий version tag на HEAD, версию
в теме и изменение package version относительно первого родителя. Эти predicates
проверяет владелец релиза на его фактическом кандидате; документационный этап
не объявляет их пройденными и не меняет реализацию ради своего PASS. Несовпадение
контракта release route и этой проверки разрешается его владельцем до
публикации, без скрытого обхода или переписывания принятых исходников.

## npm и версии

npm устанавливает опубликованные registry artifacts. GitHub служит источником
версий; tag без успешного publish и readback не является npm-выпуском. Автоматизация
релиза должна связывать точный принятый source/tag, сборку и проверку package,
публикацию и фактическое чтение registry. Потребитель выбирает npm-версию, не
готовит и не загружает отдельные архивы вручную.

SemVer описывает совместимость CLI/manifest/runtime. При обновлении необходимо
явно учитывать новые prerequisites и выбранную точную зависимость CE. Окружение должно содержать указанный Python и доступную точную зависимость CE.

До npm publish должны существовать выбранная публичная версия CE и GitHub-файлы,
на которые ведёт README. Затем проверить настоящий `npm pack`, установку именно
его `.tgz` в отдельный prefix с явным Python, содержимое README/Russian guide/skill,
schemas/templates, реальные installed origin/version и базовые команды из чужого
cwd. Private `.venv`, рабочие DB/config/INI/locks, credentials и build/bytecode
не являются материалами npm/Git. Наличие старых тестовых архивов или lock-файлов
не разрешает их публикацию.

Локальная установка через заданный wheelhouse доказывает только такой candidate.
Финальный выпуск требует проверки доступности точной зависимости, настоящей
установки из публичного registry и соответствия опубликованных байтов. Сам по
себе changelog, publishConfig или `.tgz` не доказывает публикацию.

## Documentation links

Корневой `README.md` — английский основной текст npm-страницы. Русское руководство
сохраняется в `Прочти.Меня.md`. На npm-странице использовать абсолютные URL
`https://github.com/SbWereWolf/workspace-recover/blob/main/...`; для навигации не
вставлять SHA, version tags, номера строк или относительные repository paths.
Это ссылки на текущую документацию; точные инструкции установленного выпуска
также находятся в самом пакете.

Сохранять стабильные пути docs и обоих skill-входов: полный упакованный
`skills/workspace-recover/SKILL.md` и discoverable `.agents/skills/workspace-recover/SKILL.md`.
После реорганизации оставлять по прежнему пути указатель, а не удалять публичный
адрес. Полные инструкции имеют одного владельца, wrapper не создаёт вторую копию.

Новый файл может быть корректен в source/tarball и ещё отсутствовать на GitHub.
До публикации npm-страницы владелец доставки проверяет новые пути в реально
доставленном `main`; после публикации проверяет настоящий README и переходы с
npm. Локальный link audit, raw registry README и HTTP403 при чтении страницы не
подменяют эти внешние наблюдения. Отказ в доступе фиксируется как ограничение,
а не как успешный rendered-page readback.
